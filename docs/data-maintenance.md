# 数据维护指南

本项目的核心逻辑是代码，但**难点在数据**：`data/` 下四张人工维护表决定了能覆盖多少商品、以及每个数有多可信。

出现未匹配商品时，按本文流程处理，**不要随手加进别名表**。

---

## 一、先诊断

```bash
mcd-calories gaps                       # 看有哪些未匹配，区分「已知缺口」与「新出现」
mcd-calories explain "某商品名"          # 看判定理由、全部候选与各自被淘汰的原因
```

`explain` 会列出候选及相似度。**相似度仅供人工参考，不作为自动决策依据**——实测存在「错答案相似度更高」的情况（见 README）。

---

## 二、按情况登记到对应的表

| 情况 | 登记到 | 要求 | 例子 |
|---|---|---|---|
| 与营养表某条目**语义等价**，只是命名不同 | `data/aliases.json` | 附判断依据 | `蘸酱鸡球（甜酸酱风味）` → `麦麦趣鸡球` |
| 属于某个**品类**，同类热量可共享 | `data/categories.json` | 附来源说明 | 【美汁源】饮料 → 165 kcal |
| 能**推导**出近似值 | `data/supplements.json` | **推导 + 区间 + 来源**，缺一即加载报错 | 双层脆鸡堡 520（490~560） |
| 确认**推导不出来** | `data/known_gaps.json` | 说明为什么 | 厚松饼整条产品线未收录（现已补上） |

### 决策顺序

```
该商品名与营养表某条目语义等价吗？
  ├─ 是 → aliases.json（注意：归一化能自动处理的不要写进来）
  └─ 否 → 属于某个已知品类吗？
            ├─ 是 → categories.json
            └─ 否 → 能推导出近似值吗？
                      ├─ 能 → supplements.json
                      └─ 不能 → known_gaps.json
```

## 三、三条硬性禁止

热量工具里的**错配会静默污染数值**，比承认一个缺口糟糕得多。以下三种情况**不得声明等价**：

1. **同系列不同口味的不同单品**
   例：`【美汁源】“多汁柠柠”` ≠ `【美汁源】“黄金橙橙”`（相似度 0.314，已正确拒绝）
2. **相似但不同的商品**
   例：`双层脆鸡堡` ≠ `双层吉士汉堡`（相似度 0.312，已正确拒绝）
3. **没有推导依据的数值**
   `supplements.json` 缺 `derivation` / `range` / `source` 任一项会**直接加载失败**。

## 四、写 `supplements.json` 的要求

三条硬规矩由代码强制，不是靠自觉：

```jsonc
{
  "supplements": {
    "某商品": {
      "kcal": 520,
      "range": [490, 560],          // 必填：只给点值会假装精确
      "confidence": "medium",        // high / medium / low
      "derivation": "写清怎么算出来的…",  // 必填：让人能复核
      "source": "非官方数据，不确定项…"    // 必填：不能冒充营养表数据
    }
  }
}
```

### 两种来源性质：derived 与 provided

`supplements.json` 区分两类值：

| `basis` | 含义 | 要求 |
|---|---|---|
| `derived`（默认） | 由营养表成对条目**推导**得出 | 必须能给出拆解过程 |
| `provided` | **外部给定**的点值，本项目无法独立验证 | 必须说明给定来源，并记录任何已发现的疑点 |

`provided` 的区间通常写成 `[N, N]`（点值）。**这不代表误差为零**，只表示"按给定点值采用"——
输出里会把二者明确区分（`推导估算值` vs `外部给定值`），避免读者以为它们同等可信。

若对给定值做过核对并发现冲突（例如与价格密度不符），**即使仍按原值录入，也必须把冲突留在条目里**。
留痕的价值在于：将来若发现该值有误，能立刻定位到当初的判断依据。

### 推荐做法：复用公共基准值

`supplements.json` 顶部有 `_公共基准值`，记录由营养表**成对条目相减**得出的组件值：

| 组件 | 值 | 推导 |
|---|---|---|
| 汉堡面包 | 113 | 汉堡包 248 − 牛肉饼 135 |
| 英式马芬 | 137 | 原味板烧鸡腿麦满分 246 − 板烧鸡腿饼 109 |
| 蛋 | 79 | 猪柳蛋麦满分 387 − 猪柳麦满分 308 |
| 芝士 | 46 | 吉士汉堡包 294 − 汉堡包 248 |
| 猪柳饼 | 126 | 双层猪柳蛋麦满分 513 − 猪柳蛋麦满分 387 |
| 火腿扒 | 124 | 双层火腿扒麦满分 385 − 火腿扒麦满分 261 |
| 板烧鸡腿 | 109 | 双层原味板烧鸡腿麦满分 355 − 246 |
| 脆鸡扒 | 178 | 大脆鸡扒麦满分 361 − 马芬 137 − 芝士 46 |
| 厚松饼 | 132 | 用户提供，**按片计** |

**三组独立自检**（保证基准值自洽）：

```
火腿扒麦满分 261 = 马芬137 + 火腿扒124            ✓
猪柳麦满分   308 = 马芬137 + 猪柳126 + 芝士46      ✓
猪柳蛋麦满分 387 = 137 + 126 + 79 + 46            ✓
```

新增估算值时**优先复用**这些基准值，并用**至少两种方法交叉验证**（组件加法 / 差值法 / 比例法），两法收敛才取中值。这样各条估算互相一致，而不是各自拍数。

### 消除不确定性的例子

「东南亚风味椰香鸡扒堡」早期版本把「椰香」当作可能含椰浆的**腌料**，担心额外增脂而把区间上界放到 405。经确认「椰香」就是**酱**（与其他带酱汉堡同角色）后，该顾虑不成立，区间上界收紧到 395，并把这段修正记在条目的 `_已排除的不确定性` 里——**避免以后有人重走弯路**。

## 五、改完必须验证

```bash
PYTHONPATH=src python3 -m unittest discover -s tests -t tests   # 133 项，含出厂数据加载校验
mcd-calories gaps                                              # 应无「新出现」
mcd-calories                                                   # 看覆盖率是否提升
```

`tests/test_data_files.py` 会直接加载仓库里**真实的四份 JSON**，能挡住数据写坏（漏字段、区间写反、正则无效）而不仅仅是代码 bug。

新增数据后建议补一条测试：

- 新增别名 → 断言 `tier == "alias"` 且热量正确
- 新增品类规则 → 断言命中与**不误伤**两侧（尤其是排除项）
- 新增补充值 → 断言 `low < kcal < high`

## 六、装了 WorkBuddy 之后怎么维护

装到 WorkBuddy 后，技能目录（`~/.workbuddy/skills/mcd-order-calories/`）里**有一份独立的 `data/`**。因此：

- **只改一处会漂移**：数据改动请在**源仓库**里做，再执行 `bash install.sh` 同步到技能目录；
  脚本用 `rsync -a --delete`，会清掉目标目录里多余的旧文件（幂等复装）。
- **Token 不在副本之间同步**：复制时**排除 `.env`**（避免凭据扩散）；
  只有显式传 `--token` 时才会在技能目录生成新的 `.env`（权限 `600`）。
- **两套凭据入口**：WorkBuddy 界面连接器里的 Token 供**对话调用 MCP 工具**；
  技能目录的 `.env` 供**命令行直接运行**。改了其中一个不影响另一个。
- **验证副本**：`cd ~/.workbuddy/skills/mcd-order-calories && PYTHONPATH=src python3 -m mcd_order_calories.cli --list-tools`
  会打印生效的 `.env` 路径与脱敏 Token，可用来确认副本读到了正确配置。

> 其他 Agent 渠道当前是占位（`bash install.sh kiro` 会明确报「尚未适配」并退出码 `2`）。
> 等某个渠道适配后，把本节标题与命令一并改成对应的技能目录即可。
