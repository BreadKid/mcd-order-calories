## 📖 项目介绍

**订单卡路里一览**是一个基于**麦当劳中国 MCP** 的**只读** Skill：拉取你的历史订单，
展开套餐成分，与官方营养表对齐，逐单算出热量。

算法本身只有一行 `Σ(kcal × 数量)`。真正的工作量在于**商品归一**——订单与营养表只能按
**商品名**对齐，而两边命名习惯不同（套餐容器 vs 真实成分、`可口可乐中杯` vs `可乐中杯`、
全角括号 vs 半角……）。本项目用**多级级联匹配**处理，并且
**算不出来的部分如实披露，绝不拿一个偏低的下界冒充总量**。

|        |                                                         |
| ------ | ------------------------------------------------------- |
| **输入** | 你的麦当劳账号（通过 `MCD_MCP_TOKEN`）                             |
| **输出** | 每单热量 + 覆盖率 + 每个数的来源层级与不确定性                              |
| **调用** | 仅 `order-list` 与 `list-nutrition-foods` 两个查询接口，**全程只读** |
| **安装** | 通用 Agent Skill（`SKILL.md`），一键装到 Claude Code / Kiro / Cursor / WorkBuddy 等 |
| **依赖** | 零第三方依赖，纯 Python 标准库；`clone` 下来零安装即可运行与测试                |

## ✨ 核心能力

### 1. 🧮 订单热量折算（`calories`，默认命令）

拉取历史订单 → 展开套餐成分 → 与营养表逐项对齐 → 按门店/时间逐单给出热量与覆盖率。

### 2. 🔍 覆盖率与不确定性显式披露

覆盖率不足 100% 的数值一律标注为**下界**（`≥`），并列出到底缺了哪些商品；
估算值附**区间、置信度、推导过程**。

### 3. 🧩 可审计的估算值（`supplements.json`）

营养表只收录 158 条，实际商品远多于此。能推导的按「推导 + 区间 + 非官方来源」三条硬规矩登记，
推不出来的登记为**已知缺口**，在输出中如实披露。

### 4. 🩺 单商品判定解释（`explain`）

任意商品名都能看到**判定层级、理由与全部候选**（含被淘汰的原因）——
相似度只作人工参考，**从不作为自动决策依据**。

### 5. 🤖 Agent 适配（`install.sh` + `mcp-config/`）

同一份 Skill 可通过 `SKILL.md`（负责「何时用」）、`install.sh`（负责「装到哪」）、
`mcp-config/`（负责「怎么连」）接入 Agent 工具。
**当前只适配 WorkBuddy**，其他渠道是保留的占位，后续按同一张表逐个补齐。详见 [INSTALL.md](./INSTALL.md)。

## 🎯 真正难的不是算术，是「商品归一」

算法只有一行：`Σ(kcal × 数量)`。**难点在于订单和营养表只能按商品名对齐，而两边命名习惯不同。**

| 订单里写的       | 营养表里写的         | 差异类型         |
| ----------- | -------------- | ------------ |
| 人气经典随心配     | 双层吉士汉堡 + 小杯玉米杯 | **套餐 vs 成分** |
| 可口可乐中杯      | 可乐中杯           | 少一个前缀        |
| 纯牛奶(盒装)     | 纯牛奶（盒装）        | 半角 / 全角      |
| 麦辣鸡翅2块      | 麦辣鸡翅-2块        | 连字符          |
| 那么大鸡排（椒盐风味） | 那么大鸡排          | 尾部口味后缀       |
| 【美汁源】“多汁柠柠” | *(营养表没有)*      | **覆盖缺口**     |

本项目用**多级级联**处理，每一级都有明确的采纳条件：

| 层级 | 名称                        | 采纳条件                  | 信任度 |
| -- | ------------------------- | --------------------- | --- |
| 1  | `alias`                   | 人工复核过的别名表             | 最高  |
| 2  | `exact`                   | 归一化后完全相等              | 高   |
| 3  | `supplement`              | 人工推导的估算值（附推导+区间+来源）   | 估算  |
| 4  | `category`                | 命中品类规则（蘸酱、【美汁源】、厚松饼堡） | 估算  |
| 5  | `stripped`                | 剥掉尾部括号后与营养表**完全相等**   | 高   |
| 6  | `guarded`                 | 候选经硬约束过滤后**只剩一个**     | 中   |
| 7  | `ambiguous` / `unmatched` | 多候选或没候选 → **不猜，如实上报** | —   |

用 `mcd-calories explain <商品名>` 可以看到任意一个商品名的判定理由与**全部候选**（含被淘汰的原因）：

```console
$ mcd-calories explain 那么大鸡排（椒盐风味）
判定：stripped
结果：那么大鸡排  385.0 kcal
理由：剥掉尾部括号说明「（椒盐风味）」后与营养表条目一致

$ mcd-calories explain 双层脆鸡堡
判定：supplement
结果：双层脆鸡堡  520.0 kcal
理由：命中补充热量表（本项目推导），520（490~560） kcal（medium 置信度，非营养表数据）
```

## 🔒 四条不可动摇的规则

### 1. 硬约束优先于相似度——因为错答案的相似度更高

实测数据：

```
similarity(可口可乐中杯, 无糖可口可乐中杯) = 0.732   ← 错，且更高
similarity(可口可乐中杯, 可乐中杯)        = 0.633
```

含糖与无糖只差两字，字符串上反而更「像」。如果按相似度排序取第一，**这一项会算错约 150 kcal**。

所以本项目先做**硬约束**检查（含糖标记 / 杯型 / 规格 / 数量 / 冷热），冲突的候选一律淘汰，
**且单方未标注不算冲突**（否则「可乐中杯」永远匹配不上「可口可乐中杯」）。

实际输出——注意 `✗` 那一行的相似度**比正确答案还高**：

```console
$ mcd-calories explain 可口可乐中杯
查询：可口可乐中杯
判定：guarded
结果：可乐中杯  147.0 kcal
理由：唯一候选，相似度 0.633；另有 2 个候选被硬约束淘汰

候选（相似度仅供人工参考，不作为自动决策依据）：
  ✓ 可乐中杯                  0.633
  ✗ 无糖可口可乐中杯            0.732  ← 含糖标记不一致：无糖 ≠ 含糖
```

**这就是为什么本项目从不按相似度排序取第一。**

### 2. 唯一性才自动采纳

过滤后多于一个候选，一律判 `ambiguous` 交人工，**不排序取第一**。

自动采纳门槛 0.60 是**用真实数据标定**的，不是拍的：门槛 0.30 时实测出两个假阳性——

```
【美汁源】“多汁柠柠” → 【美汁源】“黄金橙橙”（相似度 0.314）  不同口味
双层脆鸡堡          → 双层吉士汉堡   （相似度 0.312）  不同商品
```

安全区间实测为 `(0.312, 0.633]`。**宁可漏，不可错**——热量工具里的假阳性会静默污染数值，比承认一个缺口糟糕得多。

### 3. 未支付订单不计入「已摄入」

`order-list` 会返回**未支付**订单。实测账号里就有 1 条「待支付」——如果直接计入合计，
就会把**还没吃到的东西算成已经吃进去的热量**。

所以本项目把订单状态分类（规则见 `data/order_status.json`）：**只有「订单已完成」计入合计**，
待支付 / 进行中 / 已取消 / 状态未识别一律**单独展示并披露**：

```console
【已消费】计入合计
2026-09-18 12:29      482 kcal  2/2       上海康建商务广场得来速餐厅
...
==============================================================================
【待支付】**不计入合计**  —— 未支付，还没吃到
2026-10-09 17:01     ≥436 kcal  2/4    ⚠️ 麦当劳上海古浪路桃浦星品荟餐厅
==============================================================================
已消费 9 单 · 完整覆盖 9/9 单 · 覆盖商品 41/41 项 · 已覆盖部分合计 11211 kcal
未计入合计：待支付 1 单（≥436 kcal）
```

待支付订单的卡路里**仍然会算出来**——它本身是有用信息（"你有个待支付订单，约 436 kcal"），
只是不能混进「已摄入」。

> ⚠️ 另外注意：`order-list` **没有分页参数，只返回最近 10 条**。新订单会把最老一条挤出窗口，
> 所以本项目给出的是**近期窗口**内的统计，不是全部历史。

### 4. 覆盖率是硬性输出，绝不隐藏

实测某单只覆盖 1/4 项时算出 87 kcal，而真实热量在 800 kcal 以上。**只给数字不给出覆盖率会严重误导。**

所以输出永远同时给数值和覆盖率，覆盖率不足 100% 一律标注为**下界**：

```
🔥 ≥234 kcal  ⚠️ 仅覆盖 2/4 项（50%）
   ⚠️ 缺少：枫糖风味厚松饼猪柳堡、世界波脆鸡排蛋堡
   ⚠️ 实际热量显著高于此值，请勿据此做热量控制
```

## 🧩 估算值也是可审计的

营养表只收录 158 条，而实际商品远多于此。本项目用**四张人工维护表**分层处理，每层职责明确：

| 文件                 | 用途             | 要求                                  |
| ------------------ | -------------- | ----------------------------------- |
| `aliases.json`     | 订单名 → 营养表已有条目  | 需说明判断依据                             |
| `categories.json`  | 整个品类共用默认值      | 需说明来源                               |
| `supplements.json` | 单个商品的**推导估算值** | **必须附推导过程 + 误差区间 + 非官方来源**（缺一即加载报错） |
| `known_gaps.json`  | 确认算不出，如实披露     | 需说明为什么                              |

`supplements.json` 里的每个值都附带完整推导，例如**双层脆鸡堡**：

```
【基准值校准】芝士 = 吉士汉堡包294 − 汉堡包248 = 46
              牛肉饼 = 双层吉士汉堡429 − 吉士汉堡包294 = 135
              面包   = 汉堡包248 − 135 = 113       （自检 294 + 135 = 429 ✓）
【反推鸡排】  麦香鸡369 = 面包113 + 鸡排 + 生菜4 + 酱100 → 鸡排 ≈ 152
【方法A】     113 + 2×152 + 100 = 517
【方法B】     双层吉士汉堡/吉士汉堡包 = 1.459；369 × 1.459 = 538
【结论】      两法收敛于 517~538，取中值 520（区间 490~560）
```

并且**所有补充值共用同一套基准值**（面包113 / 马芬137 / 蛋79 / 芝士46 / 猪柳饼126 / 脆鸡扒178 / 麦香鸡鸡排152 / 酱85~100），有三组独立自检闭合：

```
火腿扒麦满分 261 = 马芬137 + 火腿扒124             ✓
猪柳麦满分   308 = 马芬137 + 猪柳126 + 芝士46       ✓
猪柳蛋麦满分 387 = 137 + 126 + 79 + 46             ✓
```

**每条估算都在输出里带区间、置信度和推导过程**，谁都能复核这个数是怎么来的。

## 🧪 测试

**零依赖运行**——用标准库 `unittest`，clone 下来不用装任何东西就能验证：

```bash
PYTHONPATH=src python3 -m unittest discover -s tests -t tests    # 133 passed
```

测试锁死的都是**实测踩过的坑**，不是设想的边界：

- 两个**假阳性回归**（`双层脆鸡堡`、`多汁柠柠` 必须永远被拒）
- **`相似度错答案更高`**（0.732 > 0.633）这个反直觉事实
- 含糖 / 无糖不可互配，大杯 / 中杯不可互配
- `蘸酱鸡球（甜酸酱风味）` **不是酱**，不能被酱规则吞掉 200+ kcal
- 剥掉括号后虽相等、但**含糖冲突必须拒绝**
- 覆盖率不足时必须标注下界
- 补充表**三条硬规矩**（推导 / 区间 / 来源）缺一即报错
- 品类正则写错**在加载期报错**而非静默失效
- 出厂的四份 JSON **真实加载**（最容易坏的不是代码而是数据）
- `.env` 查找与解析（换任意工作目录后 Token 仍可被读到，且**不覆盖**已有环境变量）
