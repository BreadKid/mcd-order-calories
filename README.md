## 😩 你有没有过这种经历

连着几周中午都吃麦当劳，某天突然想知道：**我这一个月到底吃进去多少卡？**

- 麦当劳 App 只显示**订单**，不显示**热量**；
- 营养表只有**单品**数据，你得自己一个个对；
- 更麻烦的是——订单里写「**人气经典随心配**」，营养表里写「**双层吉士汉堡**」+「**小杯玉米杯**」。**套餐是个容器，真正吃进去的是里面的成分**；
- 好不容易对上几个，发现还有「可口可乐中杯」在营养表里叫「**可乐中杯**」……

**这个 Skill 就是把这件事做完，而且做不完的部分如实告诉你。**

## 🎯 真正难的不是算术，是「商品归一」

算法只有一行：`Σ(kcal × 数量)`。**难点在于订单和营养表只能按商品名对齐，而两边命名习惯不同。**

| 订单里写的 | 营养表里写的 | 差异类型 |
|---|---|---|
| 人气经典随心配 | 双层吉士汉堡 + 小杯玉米杯 | **套餐 vs 成分** |
| 可口可乐中杯 | 可乐中杯 | 少一个前缀 |
| 纯牛奶(盒装) | 纯牛奶（盒装） | 半角 / 全角 |
| 麦辣鸡翅2块 | 麦辣鸡翅-2块 | 连字符 |
| 那么大鸡排（椒盐风味） | 那么大鸡排 | 尾部口味后缀 |
| 【美汁源】“多汁柠柠” | *(营养表没有)* | **覆盖缺口** |

本项目用**五级级联**处理，每一级都有明确的采纳条件：

| 层级 | 名称 | 采纳条件 | 信任度 |
|---|---|---|---|
| 1 | `alias` | 人工复核过的别名表 | 最高 |
| 2 | `exact` | 归一化后完全相等 | 高 |
| 3 | `supplement` | 人工推导的估算值（附推导+区间+来源） | 估算 |
| 4 | `category` | 命中品类规则（蘸酱、【美汁源】、厚松饼堡） | 估算 |
| 5 | `stripped` | 剥掉尾部括号后与营养表**完全相等** | 高 |
| 6 | `guarded` | 候选经硬约束过滤后**只剩一个** | 中 |
| 7 | `ambiguous` / `unmatched` | 多候选或没候选 → **不猜，如实上报** | — |

## 🔒 三条不可动摇的规则

### 1. 硬约束优先于相似度——因为错答案的相似度更高

实测数据：

```
similarity(可口可乐中杯, 无糖可口可乐中杯) = 0.732   ← 错，且更高
similarity(可口可乐中杯, 可乐中杯)        = 0.633
```

含糖与无糖只差两字，字符串上反而更「像」。如果按相似度排序取第一，**这一项会算错约 150 kcal**。

所以本项目先做**硬约束**检查（含糖标记 / 杯型 / 规格 / 数量 / 冷热），冲突的候选一律淘汰，**且单方未标注不算冲突**（否则「可乐中杯」永远匹配不上「可口可乐中杯」）。

### 2. 唯一性才自动采纳

过滤后多于一个候选，一律判 `ambiguous` 交人工，**不排序取第一**。

自动采纳门槛 0.60 是**用真实数据标定**的，不是拍的：门槛 0.30 时实测出两个假阳性——

```
【美汁源】“多汁柠柠” → 【美汁源】“黄金橙橙”（相似度 0.314）  不同口味
双层脆鸡堡          → 双层吉士汉堡   （相似度 0.312）  不同商品
```

安全区间实测为 `(0.312, 0.633]`。**宁可漏，不可错**——热量工具里的假阳性会静默污染数值，比承认一个缺口糟糕得多。

### 3. 覆盖率是硬性输出，绝不隐藏

实测某单只覆盖 1/4 项时算出 87 kcal，而真实热量在 800 kcal 以上。**只给数字不给出覆盖率会严重误导。**

所以输出永远同时给数值和覆盖率，覆盖率不足 100% 一律标注为**下界**：

```
🔥 ≥234 kcal  ⚠️ 仅覆盖 2/4 项（50%）
   ⚠️ 缺少：枫糖风味厚松饼猪柳堡、世界波脆鸡排蛋堡
   ⚠️ 实际热量显著高于此值，请勿据此做热量控制
```

## 🧩 估算值也是可审计的

营养表只收录 158 条，而实际商品远多于此。本项目用**四张人工维护表**分层处理，每层职责明确：

| 文件 | 用途 | 要求 |
|---|---|---|
| `aliases.json` | 订单名 → 营养表已有条目 | 需说明判断依据 |
| `categories.json` | 整个品类共用默认值 | 需说明来源 |
| `supplements.json` | 单个商品的**推导估算值** | **必须附推导过程 + 误差区间 + 非官方来源**（缺一即加载报错） |
| `known_gaps.json` | 确认算不出，如实披露 | 需说明为什么 |

`supplements.json` 里的每个值都附带完整推导，例如**双层脆鸡堡**：

```
【基准值校准】芝士 = 吉士汉堡包294 − 汉堡包248 = 46
              牛肉饼 = 双层吉士汉堡429 − 吉士汉堡包294 = 135
              面包   = 汉堡包248 − 135 = 113       （自检 294 + 135 = 429 ✓）
【反推鸡排】  麦香鸡369 = 面包113 + 鸡排 + 生菜4 + 酱100 → 鸡排 ≈ 152
【方法A】     113 + 2×152 + 100 = 517
【方法B】     双层吉士汉堡/吉士汉堡包 = 1.459；369 × 1.459 = 538
【结论】      两法收敛于 517~538，取中值 520（区间 490~560）
```

并且**所有补充值共用同一套基准值**（面包113 / 马芬137 / 蛋79 / 芝士46 / 猪柳饼126 / 脆鸡扒178 / 麦香鸡鸡排152 / 酱85~100），有三组独立自检闭合：

```
火腿扒麦满分 261 = 马芬137 + 火腿扒124             ✓
猪柳麦满分   308 = 马芬137 + 猪柳126 + 芝士46       ✓
猪柳蛋麦满分 387 = 137 + 126 + 79 + 46             ✓
```

**每条估算都在输出里带区间、置信度和推导过程**，谁都能复核这个数是怎么来的。

## 🚀 快速开始

需要 Python ≥ 3.9，**零第三方依赖**。

```bash
git clone <this-repo>
cd mcd-order-calories
python3 -m pip install -e .        # 可选：安装后可直接用 mcd-calories
```

**配置 Token**（在 [M-China/mcd-mcp-server](https://github.com/M-China/mcd-mcp-server) 申请）：

```bash
export MCD_MCP_TOKEN="你的 Token"
```

**开跑**：

```bash
mcd-calories                  # 订单卡路里一览
mcd-calories --detail         # 展开每单的商品明细
mcd-calories --json           # 结构化输出，便于程序消费
mcd-calories gaps             # 列出未匹配商品，区分「已知缺口」与「新出现」
mcd-calories explain 双层脆鸡堡  # 解析单个商品名，展示判定理由与全部候选
mcd-calories doctor           # 检查连通性与所需工具
```

未安装时用 `PYTHONPATH=src python3 -m mcd_order_calories.cli <子命令>`。

## 🧪 测试

**零依赖运行**——用标准库 `unittest`，clone 下来不用装任何东西就能验证：

```bash
PYTHONPATH=src python3 -m unittest discover -s tests -t tests    # 84 passed
```

测试锁死的都是**实测踩过的坑**，不是设想的边界：

- 两个**假阳性回归**（`双层脆鸡堡`、`多汁柠柠` 必须永远被拒）
- **`相似度错答案更高`**（0.732 > 0.633）这个反直觉事实
- 含糖 / 无糖不可互配，大杯 / 中杯不可互配
- `蘸酱鸡球（甜酸酱风味）` **不是酱**，不能被酱规则吞掉 200+ kcal
- 剥掉括号后虽相等、但**含糖冲突必须拒绝**
- 覆盖率不足时必须标注下界
- 补充表**三条硬规矩**（推导 / 区间 / 来源）缺一即报错
- 品类正则写错**在加载期报错**而非静默失效
- 出厂的四份 JSON **真实加载**（最容易坏的不是代码而是数据）
